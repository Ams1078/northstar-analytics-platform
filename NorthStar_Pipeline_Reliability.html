Pipeline Reliability

Reference for how the NorthStar pipeline stays healthy and recovers when it does not: run logging, watermarks, retries, idempotent re-runs, the health endpoint, and reconciliation. Implemented in pipeline_utils.py.

Pipelines

Five pipelines write to the warehouse. Each has a fixed key that matches the DataSource value on the fact rows it produces, so any published number can be traced to the pipeline that created it.

A day in the life

An illustrative nightly operating sequence. One time here is a configured schedule: the reconciliation timer fires at 05:00 UTC. Upstream processing runs in a typical window of roughly 01:15 to 04:00 UTC, and the steps in between are logical milestones, canonical resolution, publication, and watermark advancement, rather than fixed cron times. By the time anyone opens the dashboard, the night's work is already logged, reconciled, and either clean or flagged.

01:15
Bronze ingestion begins
Nightly source files are picked up and landed in Bronze, exactly as sent.
~02:00
CRM, Spend, and Ops pipelines run
The CRM, Spend, and Ops reconstruction pipelines process their respective source views and write pipeline-specific records for comparison with canonical truth.
~03:30
Canonical reconciliation
Competing source versions are resolved into the single authoritative record.
~04:00
Gold publication
Validated rows are merged into the published tables; quarantined rows are held back.
~04:00
Watermarks advance
Each pipeline records its last successful date, so the next night knows where to resume.
05:00
Reconciliation timer fires
Runs after all upstream is in. Recomputes reconciliation actions for the day and replaces that date's rows.
Morning
An operator opens the dashboard
The alert banner reflects the night. A quiet banner means no configured failure, high-severity reconciliation, or Bronze coverage alert is active.

Run logging

Every pipeline execution is recorded in pipeline.pipeline_runs. A run is opened with start_run() (status RUNNING), closed with finish_run() (status SUCCESS or PARTIAL), or terminated with fail_run() (status FAILED, with the error captured). Each call is keyed by RunId, returned from the opening insert.

Watermarks

Each pipeline maintains a watermark recording the last successfully processed date. get_watermark(pipeline_key) reads it; update_watermark() advances LastSuccessfulDateKey and sets LastRunStatus = 'SUCCESS' on completion. The watermark is how the pipeline knows where to resume and why it neither skips nor reprocesses days by accident.

Idempotent re-runs

Re-running a processed date is always safe. Gold tables are written with MERGE, so a repeated load updates in place rather than duplicating. Append-only audit tables are the exception, and clear_audit_for_rerun(pipeline_key, date) deletes that date's rows from pipeline.pipeline_flags and pipeline.silver_quarantine before reprocessing, returning the deleted counts for logging.

RuleDeletes in shared fact tables are scoped by both DateKey and DataSource. Deleting by date alone would remove other pipelines' rows for that date.

Connection resilience

The warehouse runs on Azure SQL Serverless, which pauses when idle. connect_with_retry() wraps the connection handshake with exponential backoff over four attempts (5, 15, 30, 60 seconds), so a run that arrives while the database is waking retries rather than failing.

Health endpoint

An HTTP-triggered function at /api/health returns a JSON health check. A 200 response with status = "ok" and sql = "connected" confirms the function app is live and the warehouse is reachable. It is anonymous by design so external monitors can poll it.

Reconciliation

A timer-triggered function runs daily at 05:00 UTC, after the nightly bronze loads have landed. It computes reconciliation actions for the date and replaces all rows for that date in pipeline.reconciliation_actions, so the table always reflects the latest evaluation rather than accumulating stale rows.

Action typeDetects
DEDUP_EMAILDuplicate prospect records sharing an email.
OCCUPANCY_VARIANCEOccupancy figures diverging beyond tolerance.

Each action carries a severity (high · med · low) and a status (OPEN · ACKNOWLEDGED · RESOLVED · IGNORED). Open high-severity actions drive the dashboard alert banner.
